# paintboard — 2D 像素风格画板（带实时全局光照）

游戏开发子项目。由从 Paradox Node 挖出的 `magic-simulator` 模块改造而来：
**电路模拟部分已完全移除**，保留并重写了它的 GPU 光传输管线。

## 目标

一个像素风格的画板：画出像素，由 GPU 计算光照，得到实时泛光与逐层光场。
核心（文档/工具）与渲染库解耦，游戏侧可直接复用渲染库。


- 编译器：小熊猫 C++ 自带的 MinGW-w64 GCC 11.5.0
  （默认在 `D:\Program Files\RedPanda-Cpp\mingw64\bin\g++.exe`，可用 `-Gxx` 或 `REDPANDA_HOME` 覆盖）
- 产物：`build/paintboard.exe`、`build/render_cli.exe`、`build/core_test.exe`
- 依赖的 GLFW / GLEW 静态库位于 MinGW 默认搜索路径，无需额外 `-I` / `-L`

### ⚠️ 四个必须知道的坑（都踩过了）

1. **编译器的 bin 目录必须在 PATH 上。**
   `g++.exe` 只是个驱动，真正干活的是它从 `../libexec/gcc/...` 拉起的 `cc1plus.exe`，
   而 `cc1plus` 依赖同目录下的 MinGW 数学库 DLL（libmpc / libmpfr / libgmp / …）。
   若用绝对路径调用 `g++.exe` 而该目录不在 PATH，`cc1plus` 会在加载阶段就死掉
   （退出码 `0xC000007B`，STATUS_INVALID_IMAGE_FORMAT），而 g++ **只返回一个裸的
   exit code 1，不打印任何诊断信息**。`build.ps1` 会自动把该目录前置到 PATH。

2. **不要用 PowerShell 5.1 的 `Get-Content`/`Set-Content` 原地替换源码。**
   5.1 按 GBK 读取 UTF-8 文件，会破坏中文注释**并吞掉换行**（换行被并进 `//` 注释后，
   紧随其后的代码会静默消失）。本项目已经踩过一次，5 个文件被改坏。
   编辑源码请用支持 UTF-8 的工具。`build.ps1` 本身刻意只用 ASCII 也是同样的原因——
   PS 5.1 会把无 BOM 的脚本按 ANSI 解析。

3. **`GLEW_STATIC` 必须在包含 `<GL/glew.h>` 之前定义。**
   否则 glew.h 会把函数声明成 `dllimport`，生成 `__imp___glew*` 引用，
   静态链接时全部 undefined reference。统一走 `gfx/gl_common.h`。

4. **`main` 的 `argv` 在中文 Windows 上是 GBK，不是 UTF-8。**
   CRT 按 **ANSI 代码页**（CP936）解码命令行参数，而本程序全程按 UTF-8 处理文本。
   于是 `--open 图层` 收到的是一串 GBK 字节，与源码里的 UTF-8 字面量比较**永远不相等**——
   表现是"这个选项完全没反应"，而且不会有任何报错（我自己就栽在这里）。
   现在 `app/main.cpp` 绕开 CRT，直接用 `GetCommandLineW()` 取原始 UTF-16 命令行
   再自己分词转成 UTF-8（`utf8Args()`）。顺带把 `--out 中文名.png` 这类路径也修好了。

### 四个必须知道的 ImGui 集成坑（都已踩过并写进注释）

1. **画布输入不能用 `io.WantCaptureMouse` 判断。**
   画布是一个 ImGui child 窗口，鼠标悬停其上时 `WantCaptureMouse` 会变成 `true`，
   用它做闸门会导致**永远画不上东西**。正确判据是"画布是不是当前被悬停的窗口"
   （`ImGui::IsWindowHovered()`）——它在被别的窗口 / 弹出层 / 正在拖拽的控件挡住时返回 false。
   键盘快捷键则用 `io.WantTextInput` 让路（在输入框里打字不该触发工具切换）。

2. **工作区窗口必须设成透明背景。**
   画布是裸 GL 画的，而 ImGui 在 GL **之后**渲染。保留不透明 `WindowBg` 会把画布
   整块盖住（实测表现为画布全黑）。

3. **回调安装顺序：先装宿主的，再让 ImGui 接管。**
   ImGui 的 GLFW 后端会保存并链式调用先前安装的回调（源码里的 `PrevUserCallback*`），
   所以 `installCallbacks()` 必须排在 `UiContext::init()` 之前。

4. **所有固定像素尺寸都要乘 DPI 缩放。**
   ImGui 坐标是物理像素（本程序 DPI-aware），字体与 style 已按 `uiScale` 放大；
   面板宽度若不同步放大，就会出现"字比面板宽"的溢出。

另外：刻意**关闭** `ImGuiConfigFlags_NavEnableKeyboard`，因为键盘导航会占用
Tab（切换焦点）与方向键（在控件间移动），而画板要用 Tab 开关光照、方向键平移视图。

## 光照模型

`RGBA8` 的 **alpha 是"光路上的通透程度"**，这是整个模型的枢纽：

| alpha | 含义 | 渲染行为 |
|---|---|---|
| `0` | 空气 | 光直接穿过，显示环境光 + 沿途累积的光 |
| `0 < a < 1` | 半透明介质（霓虹管、玻璃） | 光穿过并按 `rgb*a*emit` 自发光，点亮周围 |
| `255` | 实心不透明（墙、实体） | 挡住光，画面直接显示自身 albedo |

所以构造一个"灯"就是画一根 `alpha≈110` 的亮色线条；构造"墙"就是 `alpha=255` 的色块。

**`Material` 通道**：自发光强度与遮挡程度是两个独立的量，这样才能表达原来表达不了的两种像素——
「不透明但发光」（自发光墙面/屏幕）和「半透明但不发光」（彩色玻璃）。
自发光是**自己的一个 RGB 值**，不是从 albedo 派生的标量：深色表面可以发绿光、
红表面可以发蓝光，两者互不约束（见 `core/material.h` 与 UI 的「材质」分区）。

当前管线（`light_sweep`，移植自原 `renderScanline`）：

```
1. GPU 端清零 u32 定点累积 SSBO（省掉每帧 CPU->GPU 上传）
2. scan  : 一次 dispatch 覆盖所有方向（z 维 = 方向索引，曾是一方向一次共 728 次）
           每条射线直线步进，lt = lt*(1-a) + em，atomicAdd 写定点 SSBO
3. copy  : SSBO -> RGBA16F
4. blend : 与自发光合成，峰值归一，输出 RGBA8
```

## 多图层

### 编辑模型：工具只作用在**当前图层**

改造前 `Canvas` 一个类同时扮演两个角色："可绘制的表面"和"送去光照的那张图"。
有了图层之后这两个角色必须分开：

| 角色 | 类 | 谁在用 |
|---|---|---|
| 可绘制的像素表面 | `core/layer.h` 的 `Layer` | 工具、洪水填充、History |
| 所有图层压平后的结果 | `core/canvas.h` 的 `Canvas` | 光照、导出 PNG |

两个类各自持有一套语义相同的绘制原语。代价是一份**有意的、受控的重复**，换来的是
工具代码不需要知道自己写的是图层还是别的什么，而且不必为了共用而抽一个把两者绑死的基类。

流水线是 `编辑 -> 合成 -> 上传`：

```
工具改某个 Layer 的几个像素        （只弄脏那一小块）
        ↓
Document::takeDirtyUnion()        （所有图层的脏矩形合并成一个）
        ↓
flattenDocument() 只重算那个矩形   （绝不整图重算）
        ↓
Canvas 的脏矩形 -> GPU 上传        （只传那一块）
```

### 光照模型（逐层光场 + 乘法合成）

管线是**先逐层求出各自的光场、再合成**：

```
每个 Layer 各自做一轮**独立**的平面内 2D 光追
        ↓
每层得到自己的"光场" L_i —— 只有光，不含原始像素
（= 该层受光结果里的**空气像素**颜色，减掉环境光）
        ↓
自上而下把光场累加，逐层乘到原始颜色上
        ↓
按逐像素覆盖率覆盖合成
```

公式（`gfx/layer_composite.cpp`）：

```
L_i = 第 i 层的空气像素颜色 − 环境光          // 纯光，不含原始像素
F_i = Σ_{k>=i} L_k                            // 本层 + 上方所有层的光场
C_i = A_i × (F_i × strength + 环境光)         // 彩色光打在彩色表面上
acc = mix(acc, C_i, 覆盖率)                    // 覆盖 / 半覆盖
```

几个要点：

* **乘法**，不是叠加。所以只有环境光时白纸是**暗的**（`白 × 20/255`），
  符合"光没照到就是暗的"这个预期。
* 光场取自**空气像素**：那里 alpha=0 但 rgb 有值，正是这一层洒出来的光晕。
  不需要另建纹理，也不需要额外的拷贝通道。
* 环境光：每层的光场里都含一份环境光，n 层相加会过曝 n 倍。实现上从每层光场里
  **减掉**环境光，最后只在 `C_i` 里加一次 —— 等价于"每层环境光 1/n"，但不会过曝。
* 每一层都是**独立**的一轮平面内光追，层与层之间没有耦合。
* 环境光累加**是特性**（使用者自己调「环境光」控制），不额外处理。

面板「扫描 GI → **光场照亮下层**」就是这个 `strength`。默认 **1**；
下界刻意**不取 0** —— 0 是合成着色器里"关掉光场模型"的哨兵值（那条分支是旧的
加法混合），而光场模型现在是唯一路径。想要极暗的效果，0.05 已经足够。

> ⚠️ 这里修掉过一个"文档与实际不符"的问题：`App::fieldStrength` 的默认值一直是
> 1.0，但 `app/main.cpp` 里 `--field` 的默认值写成了 `0.0f`，于是**不开任何参数
> 启动画板时实际用的是旧的加法路径**（面板里那一栏显示 0.00）。现已统一为 1.0。

### 历史：旧的层间耦合（模型 B，已删除）

早先的实现是给每层算两张逐像素通道（`core/composite.h`）：

| 通道 | 含义 | 作用 |
|---|---|---|
| `occlAbove[i]` | 第 i 层**上方**各层的累计遮盖 | 给该层的平面内光线额外衰减 = 投影 |
| `emitFor_i` | 其他层的光透过**中间层**到达第 i 层的量 | 当作额外光源 = 层间照亮 |

这是**风格化**的模型（不是严格物理）。它的问题正是上面那条：空图层也会拿到
`emitFor`，于是"每新建一层画面就更亮一点"。

**这套代码已经整体删除**（`buildOcclAbove` / `buildEmitFor`、两张 occl/emit 数组
纹理、着色器里的 `u_cross` 分支、`uploadLayerChannels` 全部移除，约 300 行）。
原因：逐层光场模型本来就要求"每层做一轮独立的光追"，两者不能并存；
留着一条恒不生效、却被一个滑块意外开启的第二条路径，只会让下一个人改错地方。
对应的 8 条断言（`testLayerLightingChannels`）也一并删除。

更彻底的备选是模型 A：把层堆当成 `W x H x N` 的 3D 体素网格做真 3D 光追。
**这条路已经试过并归档**（见 `archive/README.md`）——它能拿到分图层的光线遮挡，
但整体光效不如平面内光追，为此牺牲不划算。

### 伪 3D 的 GPU 落地：逐层数组纹理

`LightSweep` 的 albedo / 材质 / 结果**全部是
`GL_TEXTURE_2D_ARRAY`**，着色器用 `texelFetch(sampler2DArray, ivec3(x,y,layer), 0)`
取任意一层，"哪一层"只是一个 uniform。这样不必为每层写一套分支，也不必把 N 张纹理
绑到 N 个 texture unit（硬件一般只有 16 个）。

`gfx/layer_composite` 用一个 compute pass 把各层按 source-over 叠起来。
留在 GPU 上是因为逐层结果有 N 张，回读 CPU 再合成会让每帧多出
"下载 N 张全画布 + 上传 1 张"的往返。

**只重算脏层**（`app/lighting.cpp`）：每多一层就多一整个光照 pass，所以那里记录
每一层的 `Layer::revision` + 可见性 + 不透明度，只有真正变了的层才重算 ——
画一笔通常只影响当前图层，代价与单层时一样。这是"实时"的关键。

单层文档时 occl/emit 恒为 0，整套公式退化成原来的平面内扫描 ——
`render_cli` 的单层路径因此与改造前逐像素一致。

### ⚠️ 一个花了很久才理清的坑：合成要按"可见度"而不是"覆盖率"

"先逐层照亮"意味着每层的受光结果里**空气像素也是有内容的** —— 那正是这一层
贡献的光晕。但空气的覆盖率是 0。如果按 albedo 的语义（alpha = 不透明度）去合成，
空气就会被当成"什么都没画"而整片丢掉：**泛光全部消失、只剩几条线**
（实测平均亮度 73 → 0.47）。

受光结果的 alpha 必须回答一个与 albedo 不同的问题：

| 数据 | alpha 回答的问题 | 空气的含义 |
|---|---|---|
| 未受光的 albedo | 这个像素有多不透明 | 空的，露出下面那层 |
| 受光结果 | 这一层的颜色要盖住下面多少 | 覆盖率为 0，但**光晕要留下** |

所以受光结果的 alpha 存覆盖率 `cov`，但**颜色本身**要包含这一层洒出来的光
（空气像素的颜色就是光晕）。合成时 `acc = mix(acc, C, cov*op)` 之外，
还要把空气那部分**加法**叠上去 —— 见 `gfx/layer_composite.h` 的推导。

### 自发光的**垂直**传输（发光像素照亮上方各层）

除了平面内的光场，还有一条**垂直**方向的光路：一个发光像素把自己的亮度沿视线
方向（Z）发出去，途中被**上方**各层的覆盖率吸收，剩下的才是相机看到的那部分。

```cpp
// gfx/layer_composite.cpp 的 kEmitComp（自上而下累乘）
transAbove[i] = Π(k>i) (1 - cov_k × op_k)     第 i 层**上方**的累计透过率
emit[i]       = 该层自发光 × 不透明度 × transAbove[i]
总自发光       = Σ_i emit[i]
```

然后由 `kEmitAddComp` **加法**叠到主合成的结果上。

三个要点：

* **它是"光"，不是"表面"**，所以是加法，不参与覆盖混合。
  第一版把它并进主合成的 `mix(acc, C, cov)`，结果被覆盖率乘了两次，
  半透明层下的发光直接少一半。
* **用不透明度加权的透过率**（`cov*op`），与主合成的覆盖规则一致；
  否则 50% 不透明的实心层会挡住光、却只盖掉一半颜色。
* **方向相反，所以单独一个 pass**：主合成自下而上，遮挡累计自上而下。
  塞进同一个循环会让主合成从"一眼能看懂"变成需要推导。

这条光路顺带修掉了两个长期存在的缺陷（都记在「已知待办」里）：

| 缺陷 | 原因 |
|---|---|
| 实心发光像素的光晕只有 1 像素宽 | 老式子 `C = A×(F+S)` 在 `cov=1` 时把 `S` 乘成 0 |
| 下方图层的发光照不到上方图层 | 发光只作为"这一层自己的颜色"参与叠加，没有垂直传播 |

实测（`scan_dump` 的单层场景）：修复前 `lit0` 平均亮度 73.82、
**最终结果 0.09**（整条发光带在黑背景上被乘掉了）；修复后最终结果 0.53、
峰值 188.8，发光带正常显示。`scan` / `lit0` 两阶段**完全不变** ——
说明改动确实只落在合成这一步。

### 怎么验证这类改动（这次教训）

只看最终画面，"扫描对不对"和"合成对不对"是同一个数字，无法区分。
所以有两个诊断工具：

| 工具 | 作用 |
|---|---|
| `tools/png_stat` | 读两张 PNG，给出平均亮度 / 亮度直方图 / 逐像素差。自带 inflate + PNG 逆滤波（环境里装不到读 PNG 的库，`stb_image` 下载回来是搜索引擎错误页） |
| `tools/scan_dump` | 把一个场景的**扫描 / 逐层受光 / 最终结果**三个阶段分别 dump 成 PNG 并报平均亮度 |

正是 `scan_dump` 报出"扫描 74.03、受光 73.35、最终 0.47"才一眼定位到合成那一步。

### 撤销重做

每个步骤是一个**补丁列表**（`Step { before[], after[], metaBefore[], metaAfter[], ... }`），
因为一次操作可能同时涉及多层。两种提交方式：

| 方式 | 用于 | 快照范围 |
|---|---|---|
| `beginStroke` / `commit` | 一笔画 | 只跟踪**当前图层**，其它层原样不动 |
| `beginAll` / `commit` | 新建 / 删除 / 合并 / 重排 / 整层清空 | 整份文档逐层快照（含图层名、可见性、不透明度、锁定） |

每个步骤同时存"改前"和"改后"两份，于是撤销与重做**完全对称**——不需要像老实现那样
在撤销的那一刻从画布现采状态（那条路一旦有绕过 History 的改动就会采坏）。

**已知限制（有意取舍，不是遗漏）**：结构性操作撤销后，"改后"状态里不包含
*当时新建的那一层的内容*。所以「新建图层 → 在上面画 → 撤销两次 → 重做两次」
会重做出一张**空的新图层**，那笔画不会回来。要修得引入真正的图层 ID
（现在图层是按索引寻址的，插入/删除会让索引整体错位，存内容反而会写错层）。

**内存**：现在每次提交存的是两份**整层**快照，与改动多少像素无关。上限仍然有界：
`320x180` 画布、128 步 ≈ `2 × 57KB × 128 ≈ 14.6 MB`，对像素画的常见尺寸完全够用，
`History::maxBytes` 还会兜底裁剪。真要省内存，正确方向是"用整层快照做差求出外接矩形，
再把两份都快照裁剪到那个矩形"。

### 图层面板

- 列表**倒序**显示（最上面的图层在最上面），`Document` 的索引 0 是最底层
- 缩略图按 `Layer::revision` 缓存：内容没变就不重传 GPU（每帧把整层转 RGBA32 是纯浪费）；
  但 revision 只管内容，所以另有一份"结构指纹"来响应顺序/增删/改名
- 下拉采样用**块平均**（不是最近邻）：像素画的细霓虹线用最近邻会在缩略图里整条消失
- 缩略图纹理用 `LINEAR` 采样（画布必须 `NEAREST`，但缩略图是缩小显示，最近邻反而更糟）

### 性能：怎么量、量到了什么

"图层数上限 16"这个数以前**没人量过**（见「已知待办」）。`tools/perf_probe` 把它变成算术：

```powershell
# 逐层渲染 / 合成分别计时，扫一遍层数
build\perf_probe.exe --size 320x180 --radius 128 --frames 50 --layers 1,2,4,8,16
# 加 --hd 会顺带给出 1920x1080 的线性外推
```

**实测（RTX 4080 Laptop，320x180，R=128 → 728 个方向）**：

| 半径 | 方向数 | 单层耗时 | 60fps 可支持层数 |
|---|---|---|---|
| 16 | 96 | 0.71 ms | 23 |
| 32 | 184 | 1.16 ms | 14 |
| 64 | 368 | 1.92 ms | 8 |
| 128 | 728 | 3.51 ms | **4** |

三条结论：

1. **成本几乎全在 `scan`（方向扫描）**。合成 pass 即使 16 层也只有 **0.1~0.2 ms**，
   可以忽略 —— 因为它的读放大是"每像素每层读 4 张"，在带宽上根本不算事。
2. **边际成本约 1.7~3.8 ms/层**，随半径上升而变大：半径越大，每条射线走得越长，
   而方向数也越多（两者都乘上去了）。
3. **实测是计算受限，不是带宽受限**。每层每帧要搬的纹理大约 2.0 MB，加合成读放大
   后 16 层也只有 ~52 MB/帧；按 3.5 ms/层算需求约 0.6 GB/s，**远低于**哪怕核显的
   25~35 GB/s 共享带宽。所以瓶颈是着色器算力（每条射线每步要做 2 次纹理取样 +
   定点原子加），会跟着 GPU 的 shader 吞吐走。

> ⚠️ 量的时候踩过一个坑：`settings().rayRadius` 只是**记下参数**，方向表是
> **惰性**重建的（要到第一次 `renderLayer` 才重建）。所以必须先跑一帧再读
> `directionCount()`，否则每个半径都读到默认值 728 —— 这个假数据差点让我
> 得出"半径不影响方向数"的错误结论。`perf_probe` 里已经把这一步固化下来了。

### 成本模型：$O(K\cdot(W+H))$，**吞吐受限**

正向扫描的复杂度是 **$O(K\cdot(W+H))$**，注意**不是** $O(N\cdot K)$：

* **一条射线 = 一个线程**，沿途把累积值原子加进经过的每个像素 ——
  所以**一条射线同时服务它穿过的所有像素**，$N$ 不出现在公式里
* 而"每像素一条射线"的反向做法是 $N\cdot O(W+H) = O(N\sqrt N)$。
  在 320×180、728 方向下，两者差 $W/K\approx 440$ 倍

**并行度扫描**（`perf_probe --dirlimit N`，射线长度固定 500 步，只改方向数）：

| 方向数 | 单层 ms | 每方向 µs | 相对 728 |
|---|---|---|---|
| 728 | 3.31 | 4.55 | 100% |
| 512 | 2.28 | 4.45 | 69% |
| 256 | 1.26 | 4.92 | 38% |
| 128 | 0.74 | 5.78 | 22% |
| 64 | 0.51 | 7.97 | 15% |
| 32 | 0.34 | 10.63 | 10% |
| 8 | 0.25 | 31.25 | 7.6% |
| 4 | 0.19 | 47.50 | 5.7% |

两个读数：

1. **64 方向以上，耗时与方向数近似成正比** —— 说明 GPU 已经喂饱了。
2. **每方向成本随并行度上升而下降**（64→728 时 7.97 → 4.55 µs，1.75×），
   说明**存在一部分延迟成分**，但它**在 256 方向左右就饱和了**，不是主导项。
3. 64 方向以下是**固定开销**（约 0.19 ms 打底）：清零 SSBO + copy pass + 多次 dispatch。

> ⚠️ **一个我自己纠正的错误**：我一度根据"364K 格访问花了 3.5 ms → 0.1 G格/秒，
> 远低于硬件能力"推断这是**延迟受限**，并据此认为"减少总工作量没用，要减少串行深度"。
> 上面这张并行度扫描表**推翻了这个判断** —— 每方向成本只降了 1.75× 就饱和，
> 不是延迟受限的典型特征（那会是数量级的下降）。
> **结论：吞吐受限。减少总工作量是有效的，加并行度收益有限。**

由此还能看出一个实用的取舍（固定总工作量的 (尺寸, 方向) 组合）：

| 配置 | 单层 ms | 每像素 ns |
|---|---|---|
| 320×180 R=128 | 3.28 | 56.9 |
| 320×180 R=64 | 1.78 | 30.9 |
| 320×180 R=32 | 1.08 | 18.8 |
| 160×90 R=128 | 0.93 | 64.6 |
| **640×360 R=32** | 3.56 | **15.5** |

同样的耗时可换到 **4 倍像素 + 4 倍少的方向**（640×360/R=32 ≈ 320×180/R=128）。
因为正向扫描里"一条射线服务多个像素"，**加分辨率比加方向划算得多**。

> 路径追踪已于 **2026-10-19** 整体移除（连同它的 next-event estimation 待办），
> 现在只有扫描 GI 一条渲染路径。下面只保留与渐进哈希采样配套的去噪说明。

### 渐进哈希采样的去噪（可选，2026-10-19）

面板「光照 → 采样方式」在开启**渐进哈希采样**后出现 **「去噪（à-trous 联合双边）」**
开关，可调「去噪强度」与「迭代层数」。命令行：
`render_cli --progressive 184 --denoise 3.5`。

实现要点（`gfx/denoise.{h,cpp}`）：

- **读累积、写独立纹理**（两张乒乓临时纹理），后面的合成通道再去读它。所以不会
  "每帧对上一帧的去噪结果再滤波"而渐进变糊。
- **引导图 = 该层覆盖率（画布 alpha）**：它没有噪声，所以光晕被平滑、几何边缘保留。
- **值域权重按逐像素噪声方差**：累积缓冲的 alpha 存 `E[luma²]`（原本空着），
  于是 `Var = E[l²] − E[l]²`，`σr = clamp(c·√(Var/N), 0.02, ∞)`。
  噪声大的像素才允许平均 —— 实测比"按亮度缩放"把 1px 结构的残差压下去 3 倍。
- 3 层 à-trous，空洞步长 1/2/4，5×5 抽头。

实测甜点（320×180、R=128、728 方向；每帧 gather ≈ 0.17× 一次确定性扫描）：
**N=2~4 帧 + 去噪** 就把光场 RMSE 从 0.155/0.092 压到 0.025/0.018（显示级 ≈1），
而原始噪声要 32 帧才追平 —— 也就是说后处理让"可接受的帧数"降了 8~16 倍。
实验工具与曲线：`tools/hash_accum.cpp`（`--scene` / `--radius` / `--scale` / `--seq`），
拼图在 `out/montage_*_r128_denoise.png`。

否则每次改动都只能靠肉眼猜。`core` 刻意不依赖 GL，就是为了让这件事成为可能。

## 调色板

内置 6 套，色值来自权威来源（PICO-8 与 DB16 已逐字节核对：

- **PICO-8**（16 色）：Lexaloffle 官方系统调色板，标准索引序 0..15
- **DB16**（16 色）：DawnBringer 2011 年原始发布值
- **Game Boy**（4 色）：社区最广为人知的"经典四色"（Aseprite 等采用）。
  注意 DMG 是反射式 STN 液晶，物理上没有固定 RGB 输出，所有数值都是近似；
  另一个有据可查的版本是 BGB 模拟器默认值（`081820/346856/88C070/E0F8D0`），
  换用它只需改 `core/palette.cpp` 里的四行。
- **NES**（55 色）：Lospec / NES.css 一致的常用近似。**不存在硬件权威的十六进制值**
  （NES 输出 NTSC 复合视频，RGB 由电视机产生），各模拟器与实测版本每一格都可能不同。
  常说的"54 色"来自另一个变体（该变体 `$37=FBDFA6`、`$3D=D8D8D8`）。
- **灰阶 8**、**黑白**

自由 RGB：`Palette::addColor()` 会把自定义色追加到当前色板末尾（P3 的拾色器界面会用它）。

### P2 当初要解决的核心问题（已完成，留档说明为什么这么做）

> 路径追踪已于 **2026-10-19** 整体移除，本节只作历史记录 —— 现在只有扫描 GI。

扫描 GI 有两个已知局限：

1. **方向性条纹**：光是沿扫描方向累积的，单个亮像素会拖出可见的直线光带，
   而不是各向同性的光晕。
2. **无法反射/折射**：只有"穿过"和"挡住"两种交互，没有折射和软阴影。

于是加了第二条逐像素 ray march 通道（真·2D 光追），复用时间累积做渐进收敛，
与实时扫描 GI 并存、一键切换；同时把光照结果与 albedo 真正解耦
（原实现是把光**叠死**在输出里，`Tab` 只是切换显示哪张纹理），
让 `Material` 的 emission / ior 真正参与计算。

实现过程中修掉的两个真问题（都能在 git log 里查到）：

- **"光线过于粗糙"**：`pos += dir` 的固定步进在斜向会整格跳过体素。
  改成 **DDA 网格遍历**，按每个格子真实的穿越长度 `dt` 加权（顺手删掉了一个魔法系数 `0.7`）。
- **"反射完全看不到"**：主射线绕过了像素自身的材质。当时的修法是加一条沿法线方向的
  `primaryMirror` 射线；后来按决定把镜面反射**整个功能移除**了，折射保留。

### 镜面反射为什么被移除

它在这个模型里始终没有一个自洽的位置：平面内的 2D 光路没有真正的"表面法线"，
硬造一个出来只会得到一条既不像镜面、又污染其它像素亮度的高亮射线。
折射（`ior`）原本依赖**路径追踪**模式通过射线方向表达；路径追踪整体移除后，
`Material` 里的 `ior` 字段仍然保留，但已不再参与任何计算。
`Material::flags` 里只剩 `kSolid`。
